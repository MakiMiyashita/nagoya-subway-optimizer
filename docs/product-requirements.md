# 名古屋市営地下鉄 定期経路探索アプリ 要件メモ

更新日：2026-09-18
状態：検討中

## 1. プロダクトの目的

名古屋市営地下鉄の定期券について，利用者が指定した予算と駅の希望を基に，発売条件を満たす可能性のある便利な定期経路を提案する．

一般的な最短経路検索ではなく，予算内で希望する駅をできるだけ多く定期範囲へ含めることを主目的とする．利用者は検索結果を見ながら条件を追加・変更し，再検索できる．

## 2. 想定する基本操作

1. 路線図上で予算と駅の条件を指定する．
2. Clingoを使って条件に合う定期経路候補を計算する．
3. カード形式で複数の候補を比較する．
4. カードを選ぶと，対応する経路を路線図上へ可視化する．
5. 結果を見て駅の条件を追加・変更し，再検索する．

## 3. 検索条件

| 条件 | 必須 | 意味 |
| --- | --- | --- |
| 定期券種別 | 必須 | 通勤，大学生，中高生，小学生以下から選ぶ |
| 期間 | 必須 | 1か月，3か月，6か月から選ぶ |
| 予算下限 | 必須 | 1区から5区までの料金区から選ぶ |
| 予算上限 | 必須 | 1区から5区までの料金区から選ぶ |
| 始発駅 | 任意 | 経路の一方の端にする駅 |
| 終着駅 | 任意 | 経路のもう一方の端にする駅 |
| 必須経由駅 | 任意 | 経路へ必ず含める駅 |
| 希望経由駅 | 任意 | 可能な限り多く経路へ含める駅 |
| 通らない駅 | 任意 | 経路から除外する駅 |

予算下限と上限の選択肢には，選択中の定期券種別と期間に対応する実際の金額を併記する．探索時には選択された料金区の範囲をClingoへ渡す．下限を設けることで，利用者が求めていない簡単で安価な経路を探索対象から除外できるようにする．

始発駅と終着駅は，経路の方向を意味するものではない．どちらも指定しない場合，Clingoが経路の両端を決める．片方だけ指定した場合，指定駅を一方の端として他方を決める．

同じ駅に矛盾する複数の役割は設定できないようにする．役割を変更した場合は，直前の役割を解除する方針を候補とする．

## 4. 探索と候補の評価

探索では，少なくとも次の条件を扱う．

- 定期券経路としての発売条件
- 予算下限と上限
- 必須経由駅の包含
- 通らない駅の除外
- 希望経由駅を満たす数の最大化

すべての希望経由駅は同じ重みで評価する．希望経由駅ごとの個別優先度は設けず，候補へ必ず含めたい駅は必須経由駅として指定する．

乗換の少なさは候補の順位付けに使用しない．ただし，発売条件としての乗換回数上限は守る．

### 4.1 解の列挙と停止条件

- 指定された料金区の範囲内にある有効な解を，原則として全解列挙する．
- Clingoでは希望経由駅の達成数が少ない解も列挙し，バックエンドで評価，整理，並べ替えを行う．
- 探索には設定可能な実行時間上限を設ける．具体的な秒数は性能測定後に決定する．
- 時間上限へ達した場合も，それまでに見つかった候補は返す．該当なしとは区別し，探索が未完了であることを通知する．
- 利用者へ返す候補は最大50件とする．51件以上の存在が分かった場合は，ほかにも候補があることを通知する．
- APIは，探索完了，タイムアウト，追加候補の有無，返却件数をメタデータとして返す．

### 4.2 重複と包含候補の除外

- 同じ経路の逆向きや，表現だけが異なる実質的に同じ経路を重複候補として除外する．
- 同じ料金区で，候補Aの定期範囲が候補Bへ完全に含まれ，候補Bが発売上の注意でも不利でない場合は，範囲の狭い候補Aを除外する．
- 料金区，利用路線，指定された端点，発売可否に関する注意が実質的に異なる場合は，単純な包含関係だけで除外しない．

## 5. 検索結果

検索結果はカード形式で一覧表示する．カードをタップまたはクリックすると，その候補経路を路線図上で強調表示する．

各カードには，次の情報を表示する．

1. 希望経由駅の達成数．例：3 / 4駅
2. 定期料金と料金区
3. 定期範囲内に含まれる駅数
4. 経路の両端の駅名
5. 乗換駅と，乗換前後の路線名
6. 満たせなかった希望経由駅
7. 発売可否に関する注意
8. 路線を表す色またはアイコン

経路の両端，路線，乗換駅は，一続きの簡易経路図として表示する．乗換情報は，例えば「高畑―東山線―伏見―鶴舞線―赤池」のように，両端と乗換前後の路線を一目で理解できる形式にする．

利用者は，少なくとも次の値で候補を並べ替え，フィルタリングできる．

1. 希望経由駅を満たしている度合い
2. 実際の料金区
3. 定期範囲内に含まれる駅数

結果内の駅名を検索し，その駅を定期範囲に含む候補だけへ絞り込めるようにする．この操作は現在の検索結果に対するフィルターであり，検索条件の変更やClingoによる再探索は行わない．実装余力に応じてMVPへ含める．

デフォルトでは，次の辞書順で候補を並べる．

1. 希望経由駅の達成数が多い候補
2. 実際の料金区が低い候補
3. 定期範囲内に含まれる駅数が多い候補

予算範囲が1区から5区の場合でも，5区の候補だけに限定せず，1区から5区までの候補を検索対象とする．希望経由駅の達成数が同じ場合は，駅数より料金区の低さを優先する．

駅数は，乗換駅を路線ごとに重複して数えず，利用可能な物理駅の数として数える方針を候補とする．

## 6. 画面方針

主要操作は単一の検索ワークスペース上で完結させる．路線図，条件指定，検索結果を同時に参照できる構成を基本とし，検索結果を見たまま条件を変更して再検索できるようにする．

モバイルを優先したレスポンシブ設計とする．スマートフォンでは路線図を中心に表示し，条件設定と検索結果は下から開くシートへ配置する．候補カードを選んだ後も，ページを移動せず路線図上で経路を確認できるようにする．

デスクトップでは，大きな路線図と条件設定・検索結果を同時に参照できる2カラム構成を基本とする．詳細は[画面遷移設計](screen-flow.md)で管理する．

## 7. 正確性と注意表示

アプリは定期券の発売可否を保証しない．交通局の規則に曖昧さがある条件を含む候補には注意を表示し，最終的な購入可否は駅または交通局サービスセンターで確認するよう案内する．
